| ADR-036 | One sale attempt (operation id + time) per version of a bill, kept across retries; any change to lines, discount or method creates a new one | The payload stays identical on retry, so the server replays instead of saving twice | 2026-10-25 |
| ADR-037 | `create_sale` input uses camelCase like the other RPCs; Phase 04 accepts quick lines only (product lines in Phase 05, udhaar in Phase 08, `offline_sync` in Phase 09); line ids are generated by the server | One code path at a time with full tests; API_AND_RPC_CONTRACTS.md §5.1 updated | 2026-10-25 |
| ADR-038 | A product line whose price differs from the catalogue is an override only when the line says `priceOverride` (needs `sale.price_override` and the shop setting, audited); otherwise `DS_TOTAL_MISMATCH {reason: price_changed, currentPricePaise}` and the app takes the new price | A stale screen can never sell at an old price by accident, and deliberate overrides stay controlled | 2026-10-25 |
| ADR-039 | `stock_movements` is created in Phase 05 (not 07); sales move stock only for products with `track_stock`; `negative_stock_policy` block / warn / allow | Voids must return stock, so movements must exist from the first product sale | 2026-10-25 |
| ADR-040 | Billing reads the catalogue through a `ProductFinder` port adapted in the composition root | Features stay independent (no cross-feature imports, lint rule) | 2026-10-25 |
| ADR-041 | Void: owner any time, manager within `void_window_minutes`, cashier never; reason 3–200 chars; sale kept and marked voided; stock returned with `sale_void` movements | Nothing financial is deleted, and late voids need the owner | 2026-10-25 |
| ADR-042 | `sales.business_date` (the shop's local date) is stored on every sale by a trigger; reports and day close group by it | Day totals must not shift at UTC midnight (05:30 IST) | 2026-10-25 |
| ADR-043 | A return refunds the line's net amount for the returned share (half up); the last return of a line refunds exactly what is left | A line's refunds always add up to what the customer paid for it, including discounts | 2026-10-25 |
| ADR-044 | CSV export is built on the phone from the report it already shows, after `begin_report_export` checks the entitlement and monthly quota on the server | No Edge Function or export bucket needed; the data is the same the user can already see, and the commercial limit stays server-side | 2026-10-25 |
| ADR-045 | An expense's id is generated on the phone and is its idempotency key; a receipt photo is uploaded first (`<shop>/<expense>/receipt.jpg`, upsert) and the expense then points to it | Retries never duplicate an expense or leave it pointing to a missing file | 2026-10-25 |
| ADR-046 | Day close is per phone per business date: expected = opening + cash sales − cash refunds − cash expenses recorded on that phone | Each phone has its own drawer/cashier; a shop-wide cash-up comes later (BL-609) | 2026-10-25 |
| ADR-047 | `products.stock_on_hand_milli` is a projection that changes only inside RPCs together with a `stock_movements` row (`private.move_stock`); `check_stock_drift` compares it with the sum of movements | Every on-hand change is explained by a movement and drift is detectable | 2026-10-25 |
| ADR-048 | Stock is tracked only for products with `track_stock`; adjustments and counts on other products are refused; purchases of untracked products only update the cost price | Most kirana items are not counted; tracking is opt-in per item | 2026-10-25 |
| ADR-049 | Suppliers have a client-generated id (`save_supplier` creates or edits) and a ledger (+ = shop owes more, − = paid); `suppliers.balance_paise` is kept equal to the ledger sum in the same transaction; the opening balance is accepted only on creation | Idempotent creation and an auditable balance | 2026-10-25 |
| ADR-050 | A purchase without a supplier must be paid in full; cash paid to suppliers (in purchases or separate payments) from a phone is subtracted from that phone's expected cash at day close | Unpaid amounts always belong to someone; the drawer reconciles | 2026-10-25 |
| ADR-051 | Customers are created and edited through one `save_customer` RPC (client id; cashiers may quick-add name + phone only); lists and the ledger are read through `list_customers` (with an udhaar-only filter, replacing `list_udhaar`) and `get_customer_ledger` | Same pattern as suppliers; one place checks permissions, quota and phone uniqueness | 2026-10-26 |
| ADR-052 | A bill with returns cannot be voided (`DS_CONFLICT`, `sale_has_returns`) | Returns already gave back stock and money (or udhaar); a void would do it a second time | 2026-10-26 |
| ADR-053 | Credit limit is optional per customer; the shop's `credit_limit_policy` decides: `block` refuses, `warn` (default) saves and warns, `none` ignores it | Shopkeepers often trust regulars beyond a limit; the owner chooses how strict | 2026-10-26 |
| ADR-054 | Customer ledger is insert-only and stores the balance after each entry plus an identity order; balance = sum of entries, updated in the same transaction; returns of credit bills may go back to the udhaar account; cash repayments count in that phone's day close | Every rupee is explainable; corrections are entries, never edits | 2026-10-26 |
| ADR-017 | Voice parsing is deterministic (grammar + fuzzy match) in v1; LLM parsing is an optional, flag-gated later addition | Predictable, offline-capable, no per-request cost, no customer data leaving device. | 2026-10-24 |
